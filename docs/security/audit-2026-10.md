# Agility security review — October 2026

Requested by Andrew after an NPR story on PHP vulnerabilities: "make sure we couldn't lose access to Agility if an AI tried to hack us." Agility is Node/Express on Render with Postgres, not PHP, so that specific story doesn't apply — but the question behind it does. This is a read-through of `server.js` (all 530-odd routes) and the library modules that were available, plus fixes for everything clear-cut. Nothing was run against the live site.

## The short version

Agility's foundations are sound: passwords are hashed with scrypt, sessions are random server-side tokens that die when a user is disabled or demoted, reset and invite links are single-use and expire, Stripe webhooks check signatures, the machine keys (ePASS agent, snapshot, website feed) are compared timing-safe and refuse when unset, every SQL query is parameterized (972 checked — none build SQL from request text), no shell commands are run, and uploads go to Postgres with size limits. The audit log can't be deleted from inside the app.

The findings fall into three groups. A handful of real holes that an automated attacker would find quickly (fixed in this delivery). A list of environment settings on Render that decide whether the remaining defenses actually hold (you need to check these — five minutes). And things I could not see from here (package versions, about half the library files) that need one more pass when the laptop is back online.

The honest framing on "an AI hacking us": the realistic attack is not a clever exploit, it is automation — thousands of password guesses, stolen passwords from other sites tried against Agility logins, scanners probing every public form, and phishing a staff member for their password. Everything below is aimed at making those cheap attacks expensive and making sure that even a successful one can't lock you out.

## Fixed in this delivery

**Signed-cookie secret had a guessable default (High).** If `SESSION_SECRET` isn't set in Render, the key used to sign the legacy "wilson" login cookie and the break-glass fallback cookie was literally `wilson:<store password>` — and a cookie claiming to be an executive was honored forever. Anyone who knew the store password could forge an all-access login with no database row and no audit trail. Now: `SESSION_SECRET` is used when set; otherwise a random secret is generated at each boot and the log shouts about it. Legacy cookies also get a server-enforced 12-hour cap, and an "executive" legacy cookie is only accepted for the break-glass account while break-glass is configured. Database sessions never depended on this secret, so normal logins are unaffected. **Action for you: set `SESSION_SECRET` in Render (see checklist).**

**Rate limits could be dodged by spoofing the IP address (High).** Render's proxy appends the real address to `X-Forwarded-For`, but Express was reading the first entry — which the client writes. A bot could rotate a fake address every request and never hit the 10-tries-per-15-minutes login limit, or spend the showroom's real address on bad logins and lock the whole office out. The server now takes the right-most public address in that header (the one Render added), for every limiter, the audit log's IP column, and the website feed's IP allow-list.

**No per-account lockout, no record of failed logins (High).** Ten wrong passwords for one sign-in name now locks that name for 15 minutes (same error wording, so the guesser can't tell), and every failure is written to the Audit Log as `login_failed` with the address. The break-glass account is exempt from the lock when the password is correct, so nobody can lock the recovery login by hammering it. Logins through the shared login and logouts are now audited too.

**Path trick could read source files without logging in (High).** The static file server serves the repo folder, with a deny-list for `server.js`, `lib/`, `data/` and so on — but the deny-list looked at the path as sent and the file server normalized it, so `/events/../server.js` passed the deny-list as "events" (a public prefix on the service host) and was served as `server.js`. Confirmed in a local test. Paths containing `..`, backslashes or bad `%` escapes are now refused before anything else looks at them; the deny-list also covers more extensions (`.mjs`, `.ps1`, `.yml`, `.pem`, `.key`, `.map`, `.zip`, `.db`…) and folders (`odbc/`, `deliver/`, dot-folders), and the `/events` prefix no longer matches `/eventsanything`.

**Shop sign-in by phone + last name skipped the password (Medium).** A shopper who had set a password could still be signed in by anyone who knew their phone number and surname — public facts — which exposed their profile and let the attacker change the password. Profiles with a password now require it; profiles without one keep the easy path.

**Any executive could re-point another executive's login to an outside email (High).** The employee-directory save moved the login account to the new address with no company-domain check, no session kill, and reset tokens left valid — so one compromised executive session could take over every other executive's account via password reset in minutes. Email changes now require the company domain, end that account's sessions, and void every outstanding token. There's also a **last-executive guard**: the app refuses to disable or demote the last active executive, so an attacker can't leave themselves as the only admin.

**Image uploads trusted the browser's file type (Medium).** Any `image/*` was accepted and served back inline — including SVG, which can carry scripts and would run as the signed-in reviewer who opened it. Two public forms (service request photos, quote media) accept uploads from outsiders. Uploads must now be a real photo type (JPEG, PNG, HEIC, WebP, GIF…), and every stored file is served with a Content-Security-Policy that forbids scripts and forces anything non-photo/non-PDF to download rather than render.

**Sub-Zero inquiry form was a texting relay (High).** It sends a confirmation text to whatever phone number the form gives, throttled only per (spoofable) IP. Now capped at 2 texts per phone number per day and 30 per hour in total, and only letters from the first name reach the message.

**60 MB bodies were buffered before the key was checked (Medium).** The ePASS agent and snapshot upload endpoints parsed the full body before looking at the key, so anonymous posts could tie up memory. The key is checked on the headers first.

**Also fixed:** Samsara webhook key compared non-timing-safe; PDF text extraction could be fed a decompression bomb (`inflateSync` now capped at 32 MB); all CSV exports neutralize spreadsheet formulas (a customer note starting with `=` no longer executes when staff open the export in Excel); `cors()` answered `*` to every origin — now only the three Wilson hostnames; HSTS and Permissions-Policy headers added; the shared "wilson" login has been **removed entirely** (same day, Andrew's call) — it was one password known to many people that opened nearly every page including refunds and card charges; every staff member now signs in individually and every action in the Audit Log has a name on it; the page-grant check runs on every hostname (it skipped non-dashboard hosts); registering with an invited colleague's address can no longer pre-set their password; `STORAGE_MODE` defaults to postgres when a database is configured (the old default, `json`, would have silently written payment links to Render's throwaway disk if that variable were ever lost); rate limits on every public form that creates Stripe objects, tickets, or sends anything; and a process-level safety net — a database hiccup in a background job no longer crashes the server and logs everyone out, and route errors return a clean message instead of a stack trace.

## Render environment checklist (you)

These decide whether the above holds. Render → Agility service → Environment:

| Variable | What to do | Why |
| --- | --- | --- |
| `SESSION_SECRET` | Set to 64 random characters (PowerShell: `-join ((1..64) \| ForEach-Object { '{0:x}' -f (Get-Random -Maximum 16) })`). | Without it, legacy/break-glass cookies reset on every deploy (safe, but noisy). |
| `APP_USERNAME`, `APP_PASSWORD`, `LEGACY_SHARED_LOGIN_ENABLED` | Delete them. | The shared "wilson" login was removed from the code on 10/24 (Andrew's call); the server no longer reads these. Any browser still holding a shared-login cookie is simply signed out. |
| `EXECUTIVE_PASSWORD` | Make sure it is set, long (20+ random characters) and in your password manager. | This is the break-glass login: it works even with the database down and recreates your executive account if someone deletes or demotes it. **If it's missing, there is no in-app recovery** — only direct database access. |
| `STORAGE_MODE` | Confirm it says `postgres`. | Payment-link records live in Postgres only when it does. |
| `INVENTORY_FEED_ALLOW_IPS` | Optional: the website vendor's outbound IPs. | Second lock on the inventory feed; it only works now that the IP fix is in. |

On Render → the Postgres database: confirm the plan includes **point-in-time recovery / daily backups**, and know how to restore. There is no in-app backup of users, payment links, service jobs or commissions — the database backup is the only recovery path for a bad write or a malicious delete.

## How you get back in if someone does get in

Break-glass: sign in with `EXECUTIVE_USERNAME` (your email) and `EXECUTIVE_PASSWORD` from Render. It bypasses the database password, re-activates and re-promotes your account on every login, and if the database itself is unreachable it falls back to a signed 12-hour cookie. From there: User Admin → disable the compromised account(s), force a password reset on everyone, then change `SESSION_SECRET` in Render and redeploy (this kills every legacy cookie; database sessions are already revoked by the disable). Check Audit Log for `login_failed`, `login`, `permissions_updated`, `executive_granted` entries to see what was done. The audit table cannot be deleted from inside the app.

Secret rotation never requires a code change — every key is an environment variable plus its counterpart (Stripe dashboard, Resend, Podium, `epass-agent.key` on the showroom share, the snapshot script on the store PC, the website vendor). Rotating the agent key: update the key file on the share first, then Render, then move any files the agent parked in `failed\` back to the outbox.

## Not done yet

- **Package versions — checked 10/25 once the laptop was back.** Good news: `xlsx` is the fixed SheetJS build (0.20.3 from cdn.sheetjs.com, not the vulnerable npm one), `express` 4.22.2, `pdfjs-dist` 6.2.108, `stripe` 18.5, `pg` 8.20 are all current. One item: `multer` is 1.4.5-lts.2, and the 1.x line has three 2025 denial-of-service advisories (malformed uploads can leak memory or crash) fixed in 2.0.2. Every upload here is memory-storage with a size cap, which blunts it, but the upgrade is cheap: in `C:\dev\wilson-agility` run `npm install multer@^2.0.2`, then push — the code needs no changes (same `multer.memoryStorage()` API).
- **About 37 library files** weren't in my copy (`lib/data.js`, `lib/podium.js`, `lib/samsara.js`, `lib/credit-app-postgres.js`, `lib/events-postgres.js`, and others). The `BCA-XXXX-XXXX` credit-application resume code looks short enough to guess — check how it's generated. Whether `lib/data.js` reads `STORAGE_MODE` on its own (my default change is in `data-postgres.js`).
- Two `innerHTML` spots on the dashboard queue render staff-typed customer/employee names without escaping (insider-only). One-line fix each; left for the next dashboard change so I don't overwrite a version I couldn't re-read.
- A Content-Security-Policy for the pages themselves (they use many inline scripts, so it needs a nonce scheme — a project, not a patch).
- No idle timeout on sessions (12-hour absolute only) and no self-service password change; both are nice-to-haves.
- Commute miles are self-editable via Profile and feed mileage reimbursement math — probably should be executive-only. Business decision.
